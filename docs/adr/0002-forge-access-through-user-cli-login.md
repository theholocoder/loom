# Loom acts on the Forge only through the user's own git/gh/glab login

Users log in to Loom with Forge OAuth, but that login only proves who they are and which Team they belong to: the Server uses it for identity and org/group membership, and the Client holds no Loom forge token. Cloning, pushing, opening and looking up Merge requests, fetching issues and Babysit all go through `git`, `gh` and `glab` authenticated as the user. We considered giving Loom's OAuth app write scopes and keeping short-lived forge tokens on the Client, but that means broader app permissions, token refresh and a git credential helper, for no gain: the agent already uses the user's CLI login, and this way Loom has exactly the user's access, nothing more. The cost is that every Client needs working `git`/`gh`/`glab` auth for each Forge host, which Loom checks and warns about.
