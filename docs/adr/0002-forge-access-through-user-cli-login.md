# Loom acts on the Forge only through the user's own git/gh/glab login

Loom has no login of its own and holds no forge token. Cloning, pushing, opening and looking up Merge requests, fetching issues and Babysit all go through `git`, `gh` and `glab` authenticated as the user. We considered a Loom OAuth app with write scopes and short-lived forge tokens on the Client, but that means broader app permissions, token refresh and a git credential helper, for no gain: the agent already uses the user's CLI login, and this way Loom has exactly the user's access, nothing more. (Loom first kept Forge OAuth for identity and Team membership on its Server; both went away with the Server in ADR 0006.) The cost is that each Forge host needs working `git`/`gh`/`glab` auth, which Loom checks and warns about; without it, that Project's Forge features stay off.
